むしゃ×むしゃ (2001/07/29)

このページ(いやはやまった)は、 何のページかと言うと、本来、プログラムサイトであるわけで、 文書がメインというわけではないです。 が、最近はどうも変にテキストサイトを意識して、 なんとか週刊更新を維持しようとしてしまった結果、 少々無理をしてしまったようです。

やはり、ここいらで、日本語が下手な輩(=ワタシ)は、それらしく、 フリーソフトウェアを地道に書くのが道というものでしょう。 あまり、調子に乗って、日記ばかり書いていると、

職場でさらしものにされます

だから、言いたくなかったんだよ (←とここで書く自体もうハマっているような気もするが)。 あ、言っておきますが、職場で書いているわけではないですよ！ たまたま、サンプル用 PNG 画像が必要だったんで…

ということで、本来の道へ帰るべく、 NYADOS/NYAGOS を Ver.UP しました。 NYADOS では NYAOS のころからの念願だった単独シェル化を実現しました。 が、dir や type が使えなくなったり、まだ不安定でもあったりしますので、 option standalone 1とした時のみ有効です。 また、NYAGOS では実現できていません。 CMD.EXE だと、パイプはメモリ上のバッファを介して実現されるので、 NYAGOS でもそう実装しようとしているのですが、うまくいかないんですよね。 ちなみに NYADOS ではテンポラリファイルを使っています。 他には、入れ子可能な foreach とか set +=,-= とか、 NYAOS で実現していた機能も一部実現しました。 あ、-= は実現してないか。

こうして、NYAOS の機能を NYADOS で復活させてゆくと、 NYAOS ではいかにプログラムを細かく書きすぎて、 いらぬ苦労をしていたのかが実感させられますね。 具体的には NYAOS では文字列は極力 char配列でやっていたわけですが、 NYADOS , NYAGOS では自前の文字列クラスを使ってます。 また、可変長配列クラスを活用した結果、 realloc とか、リスト構造の維持で要した手間が全くなくなりました。

と、つらつら思うに、NYAOS 作成当時は、結局のところ、たいていの C言語出身者にありがちな実行効率至上主義に陥ってしまい、 開発効率やソースの見とおしを台無しにしておりましたなー。 少々ヒープが断片化したところで、今日のマシンだと 蚊にさされたほどの実行効率のダウンもないというに。 よくこんな書き方でシェルが作れたもんだと、逆に感心したりなんかして。

★≡≡≡≡

なんか、プログラムの一つでも書けば、本ページの品があがるかなー ということで、他の UNIX系サイトのようにシェルスクリプトの一つでも書いてみやふ。 ちなみに、これは昨日書いて喜んでいた、 DBデータを select した結果を CSV に落とすスクリプトの基本骨格をあいまいな記憶を元に今復元(お〜い) 

    #!/bin/sh
    grep -v '^#' <<__EOF__ | sqlplus hoge/hoge | nawk '
        /CVS:/{
            print substr($0,5)
            ++count
        }
        END{
            printf "%d",count
        }
    ' > table_list.cvs
        set heading off
        # linesize は間違っているかも
        set linesize 1024
        # SQL だよ〜ん
        select  'CVS:'||o1.column1||','||o2.column2||','||o2.column3
          from  our_table1 o1 , out_table2 o2
         where  o1.column4 = '1'
           and  o1.serial = o2.serial;
    __EOF__

SQL が複雑な場合でも使える最も手軽な方法はこれかなーと勝手に思っているけど、 もっと簡単な方法があったら、誰か教えて欲しい。 こんなん載せても喜ぶのは、同僚だけのような気がしないでもないが。 まぁ、全ての我が自己満足のため。 (読まされる方はたまったもんではない;-)

まぁワタシのことだから、C++ Builder をどうのこうのする以前に挫折するに決まっているので、実のところ、議論するほどのことではないのですけれども＞ Averageさん。

「言語がサポートできる情報もむりやりプログラマ側が管理する形」となっているのは、C++ が C 言語から受け継いでいる思想「プログラマを信頼して実行コードの効率をあげる」ためですから、別にそれはそれでいいと思いますけどねぇ。ただ、それが日常的 GUI プログラミングに良いかというと、それは異議ありで、そういうのには C++ は不向きだと思います。だから、C++ Builder を食わず嫌いしていると。

おぉ、なんか知らんが
一見、理屈があってそうに見えるぞ

C++ は余り富豪的プログラミング向き言語ではないですからね。どっちかというと、スクリプト言語が一番いいでしょう、こういうのは。 (我ながら、ちょっと定義に誤解がある可能性大)

と、以上、自分の都合のいいところだけ(つーか書きたいことだけ)、反応してみました。 Pascal については、ワタシよー分からんので、きっとおっしゃる通りなのでしょう。 でも、0.1秒のコンパイルが0.01秒になってるご時世ですから、 速さのメリットは段段小さくなってゆく可能性も無きしもあらず… (と嫌なことを書いてみる奴…友達減るぞ！＞自分)
