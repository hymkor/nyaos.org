NYA☆S のソースの歩き方

や めときゃいいのに、日本語拡張コマンドラインシェル NYA☆S のソースリストの解説をする。果たして参考になるか、役に立つか、はなはだ疑わしい限りであるが。

NYA☆S のソースファイルは大きく分けると４つに分けられる。

  • 共通ライブラリ
    NYADOS はその動作環境ゆえに、STL など巨大クラスライブラリを使用するのが困難である。そこで、Turbo-C++ のクラスライブラリをベースに独自の小さなライブラリ Nihongo Nano Library を用意している。(nnstring.cpp nnvector.cpp nnhash.cpp nnstrhash.cpp nndir.cpp reader.cpp writer.cpp)
  • 一行エディター部
    NYADOS のキモッ…ではなく、肝であるところの一行エディターである。ベースは eff のものである。ヒストリは、一応、一行エディタ部に所属し、API を次のインタプリタ部に公開する形となっている。(getline.cpp twinbuf.cpp getline2.cpp dosshell.cpp history.cpp keybound.cpp keyfunc.cpp ntconsole.cpp xscript.cpp )
  • インタプリタ部
    構文解釈部・実行部・各コマンドの処理などがある。あるなぁ。(mysystem.cpp wildcard.cpp cmdchdir.cpp commands1.cpp commands2.cpp which.cpp scrshell.cpp shell.cpp shell4.cpp shellstr.cpp ishell.cpp foreach.cpp)
  • その他
    全体を統括するメインルーチンですな。(nyados.cpp)

以下でそれぞれのパートを解説する。結構でかそうだけど、できるかな。

共通ライブラリ

共通ライブラリは、NYA☆S を作成するにあたり、まず最初に着手したものである。Turbo-C++ のライブラリをベースにし、Java のクラスライブラリを参考にし、貧乏性な精神で育んだため、次のような特徴を持っている。

  • 所有(ownership/delete義務)という概念を持っている(Turbo-C++由来)
  • 参照よりも、ポインタをメインに使っている(Javaの影響*1 )
  • 日本語をフルサポートしている。
  • 必要なクラスだけに極力限定している(DOSで使うため)。
  • キャストを使いまくらなくてはならない(Javaの影響)
  • 演算子のオーバーロードを<<を除いて、ほとんど使用しない(Javaの影響*2)
  • テンプレート , dynamic_cast , 例外など、最新の C++ の機能を一切使用していない。

などがある。構成としては

  • 文字列クラス
  • コンテナクラス
  • 入出力クラス

からなる…と思う。基本的なクラスの継承関係は次の通りである。

      NnObject (オブジェクト)
        ┣ NnSortable (比較可能オブジェクト)
        ┃   ┗ NnString (文字列)
        ┃   　 ┗ NnStringIC (英大文字/小文字を区別しない文字列)
        ┣ NnVector  (可変長配列)
        ┣ NnHash NnStrHash (文字列キーのハッシュ)[2003.11.30修正]
        ┣ NnHash::Pair NnBullet  (文字列キーと値のペア)[2003.11.30修正]
        ┣ Writer    (汎出力)
        ┃   ┣ FileWriter    (ファイル出力:NYADOS版)
        ┃   ┗ StreamWriter  (FILE*出力)
        ┃      ┣ FileWriter (ファイル出力:NYACUS版)
        ┃      ┗ PipeWriter (パイプ出力)
        ┣ Reader    (汎入力)
        ┃   ┗ StreamReader  (FILE*入力)
        ┃      ┣ AnsiConsoleWriter (コンソール出力) [2003.11.30追記]
        ┃      ┣ FileReader (ファイル入力)
        ┃      ┗ PipeReader (パイプ入力)
        ┗ NnEnum    (イタレーター)
             ┣ NnHash::Each NnStrHash::Each (ハッシュの各要素 → NnHash::NnBullet ) [2003.11.30修正]
             ┗ NnDir           (ディレクトリ     → NnString )

当初の意図を越えて、やたら大きくなってしまった。特に Writer , Reader は入出力を仮想化したものだが、stdio のファイルハンドル操作だけ(dupとか)で代用できるかもしれず、正直これは不要だったように思われる。

クラス名の前についている Nn は、Nihongo Nano Library を意味する。

というのは建前で、単純に String 等と名乗ると、どっかで名前がぶつかりそうなので、それを避けてのことである。そうすると、適当な接頭語をつけなくてはいけないわけだが、あまり長いとタイプするのが面倒だし、かといって、１文字とするとありがちだし…ということで、入力しやすく、かつ格好よさそうな名前をつけたいのが人情である。結局、同じ文字を並べて、Nn という語で落ちついたわけだ。

NnObject と NnSortable

トップの NnObject が全てのオブジェクトの既定クラスである。コンテナに格納できるのは、これを継承したクラスオブジェクトに限られる。NnObject が持つメソッドは３つしかない。デストラクタと clone と sortable である。


class NnObject {
public:
    virtual ~NnObject();
    virtual NnObject   *clone() const;
    virtual NnSortable *sortable();
};
clone は自らの複製を作るものだが、実はあまり使われていない。sortable はもしオブジェクトが大小関係を持つものであれば(NnSortable を継承したオブジェクトであれば) 自分を NnSortable* に単純キャストしたポインタを返す。さもなければ NULL を返す。要は dynamic_cast<NnSortable*> の代替品である。 

class NnSortable : public NnObject {
public:
    /** x と比較して、大小関係を 負・零・正の数値で返す。*/
    virtual int compare( const NnSortable &x) const = 0;
    virtual NnSortable *sortable();
};

NnSortable は NnObject に対し、比較するためのメソッド compare を加えたものである。それだけ。これを継承したクラスは実は文字列しかない。

NnObject , NnSortable の二つのクラスは宣言は nnobject.h , 定義は nnstring.cpp 内にある。nnstring.cpp 内にあるのは、本クラスライブラリの肝は文字列クラス NnString にあり、これを利用しないことはまずありえないからだ。

文字列クラス NnString

クラス宣言は nnstring.h 、クラス定義は nnstring.cpp にある(が、ある一つのメソッドだけは nnvector.cpp にある)。

この文字列クラスの特徴は

足し算の二項演算子(+)がない！

につきる。足し算の代入演算子(+=)はあるけどね。足し算演算子は分かりやすいが、一時オブジェクトの生成/消滅を激しく伴うため、利用コストが高いのである。その代わりに用意したのが、挿入演算子 << である。STL だと


    string foo,bar("ほげ"),boo("うは");
    foo = bar + boo;
    printf("%s\n",foo.c_str() );

と書くところを


    NnString foo,bar("ほげ"),boo("うは");
    foo << bar << boo;
    printf("%s\n",foo.chars() );

と記述する。可変長文字列の用途は、末尾末尾に文字列を追加してゆくことが大半であるため、これでたいていはこれで用が済む。それほど可読性が落ちているとは思えないのだが、どうだろうか。

chars() は、char配列へ変換するメソッドである。本クラスから char 配列への自動変換はされない。キャスト演算子 operator const char() を定義すれば、明示的に記述せずとも、そのまま標準Ｃライブラリを利用できる。が、キャスト演算子は、下手に定義すると、C++ コンパイラが思わぬ変換をしてしまうケースがあるため、結構こわいところがある。STL でも c_str() を用意したのはそのせいであろう。

コンテナライブラリ

といっても、コンテナクラスは二つしか存在しない。

  • 可変長配列 - NnVector
  • 連想配列 - NnHashNnStrHash

専門書を読むと、代表的なデータ構造としては、他にリスト構造、ツリーなどがある。が、だいたいの場合は、この２種だけで事足りてしまったりするのである。

可変長配列 NnVector

NnVector は、Java の Vector を意識した可変長配列クラスである。宣言はヘッダファイル nnvector.h , 定義は nnvector.cpp に記述されている。正直あまり特徴はない。


    int main()
    {
	NnVector array;
	array.append( new NnString("hogehoge") );
	array.append( new NnString("hogehoge") );
	for( int i=0 ; i<array.size() ; ++i ){
	    printf("%s",(NnString*)( array.at(i) )->chars() );
	}
    }

実をいうと、このクラス、operator[] をメソッドとして用意しておらず、 at という普通のメソッドを用意している。正直、オーバロードを使うと、クラスオブジェクトなんだか、そうでないのか、ソースを見てすぐ分からなくなってしまうため、敢えてそうしている。

また、テンプレートを使っていないため、取り出した後、なんとキャストしなくてはならない。なんでかというと… Turbo-C++ がテンプレートをサポートしていなかったためだったりするのが、そもそもの理由だったりする。まぁ、NnVector をラッピングするクラスをテンプレートで作るという方法もあったが、Java では平気でキャストしていたため、まぁそれほど問題視しなかったことが大きい。

さて、もう一つ気になる点としては、配列に要素を足す際に文字列をわざわざ new しているところがある。array.append("hogehoge") ではだめなのだろうか。これには、オブジェクトの所有という概念が関係している。

所有

STL 等では、コンテナライブラリにオブジェクトを格納する際に、オブジェクトの「複製」を格納する。これのメリットとして、１オブジェクトがコンテナ内とローカルの２箇所から参照されているようなことがないため、互いの挙動を気にすることなく、いつでもオブジェクトを破棄できるという点がある。これは int とか short 等の組み込み型のように扱えることを意味し、あまりメモリ管理を意識しないで済むということを意味する。

が、格納の際に必ずコピーが行われるため、使用コストがそれなりに高い。最近の OS 環境であれば問題ないが、DOS をプラットフォームとするNYADOS の場合、そのコストは無視できない。

NYADOS のコンテナライブラリはポインタベースとなっている。たとえば、コンテナにオブジェクトを格納する場合は、オブジェクトのポインタを渡すわけである。この時、そのオブジェクトを delete する義務(所有権)は、呼び出し元からコンテナオブジェクトへ移動する。

つまり、AUTO なオブジェクトはコンテナへ格納できないのである

コンテナへ格納する可能性のあるオブジェクトは原則的にnew したものでないといけないのである。

さて、逆にコンテナからオブジェクトを取り出す際には２通りのケースがある。

  • 所有権が取り出す側へ移動するケース
    これはオブジェクトが呼び出し元へ移動する場合である。呼び出し元はオブジェクトを得るが、その変わり、オブジェクトはコンテナから消え失せる。そのオブジェクトは最終的に呼び出し元が delete しなくてはならない。
  • 所有権はコンテナにとどまるケース
    オブジェクトがメソッド呼出し後も依然としてコンテナ内にとどまる場合がある。この時、呼び出し元はそのオブジェクトを参照・変更することはできるが、delete だけはしてはならない。

以上のケースの区別はメソッド単位で規定する。ヘッダファイルを見れば、呼び出し元で delete する必要がある場合はその旨がコメントとして必ず書いてあるはずなので、読んでみましょう。

連想配列クラス NnHashNnStrHash

宣言は nnhash.hnnstrhash.h , 定義は nnhash.cppnnstrhash.cpp である。このクラスの最大の特徴は、キーとして文字列(char[],NnString)しかとらない点である。

世の中、大半の連想配列は、キーとして任意のオブジェクトを利用できるようになっているが、筆者は正直、文字列以外がキーとして用いられたケースを一度も見たことがないためである。

基本的な使い方は簡単である。


    NnHash hash;
　
    hash.put("キー",new NnString("実体") );
    NnString *obj=(NnString*)hash.get("キー");
    if( obj != NULL ){
	printf("見付かった.(%s)\n",obj->chars() );
    }else{
	printf("見付からなかった.\n");
    }

put で登録し、get で取得する。ただし、get をした後もオブジェクトの所有は依然として hash 内にある。

put の第一引数のキーは char配列を直に書いている。これは所有ルールの唯一の例外である。put メソッド内で、引数の複製である NnString オブジェクトを作成して格納している。キーに対応するオブジェクト(第二引数)の方はルール通りに所有がhash 内に移行する。オブジェクトが delete されるのは hash が消滅するタイミングである。
