  • 「形式知」と「暗黙知」
    otsune 氏の見解に概ね賛同。ただ、何かマニュアルという言葉には語弊があるようにも思えますね。私が、ソフトを作成する上で、マニュアルを意識した時、次を考えます。
    1. マニュアルを書かないで済むよう本体の機能を分かりやすくする
    2. マニュアルに書かねばならぬことを漏らさず書く
    さて、これで全て分かるかというと、そうではなく、パーフェクト利用者は内部の（1. にて省略された、普通は知らなくてもよいような）構造まで理解した上で、想定されない使い方を編み出し、原作者を驚かすことがあるのです。おそらく、こういうのも含めて暗黙知になるのかと。
    ならば、そういう内部構造までマニュアル化すべきという考え方もあるかと思います。それは全く正しいと思いますが、用語を改めなくてはならない。もはやマニュアルではなく、一般化した「ドキュメント」ですね。

YAOS-II 2.18 で、SHIFT+インサートキーが認識できないというバグリポートをいただきました。S2NYAOS でも発生する現象のようで、どうやら入力キーの読み取り方式に依存するようです。emx/gcc で私が使っているキー入力方法として

  • UNIX ライクな端末制御によるキー入力(termio) → NYAOS-I 1.65
  • _read_kbd 関数 (emx/gcc オリジナル関数) → S2NYAOS 1.65
  • getch 関数 → NYAOS-II

があります。で、最初の端末制御方式では SHIFT+インサートキー は認識できるようですが、他ではどうも単独のインサートキーと区別できないようなのです。

ならば、端末制御方式にすればよさそうなものなんですが、これを用いると、動作時に emx.dll が必要になってしまうのです。「１個の実行ファイルで手軽に UNIX ライクなコマンドラインを」というのを新ポリシーにしたばかりですし、これは困りました。

YA☆S 2.18 をリリースしました。OS/2 ユーザにとっては NYAOS-I でお馴染みの open コマンドが復活しました。これは GUI 操作でダブルクリックするのと同じことをコマンドラインから行うコマンドです。Windows では start やら explorer コマンドで等価なことができますので、どちらかというと、機能/操作の統一という意味での実装となります。

とは言いつつ、NYADOS では残念ながら本コマンドはカットしました。16bit アプリケーションなので、直接の実現は無理で、system関数経由で startコマンドと explorerコマンドを選択して呼び出して、エミュレートさせようかとも思いました。ですが、OS のバージョンによって結構挙動の違いがあるのに、Windows95 環境が今日中に用意できなかったので、とりあえず今回は見送りました。*7

NYACUS では、プロンプト(PROMPT)や print コマンドで簡易ながらもエスケープシーケンスを使えるようになっています。これは内部的なエミュレーションで、外部コマンドでは使えませんが、list 以外で明示的に色を制御できると結構便利だと思います。

他、一つ二つ虫繕いをしています。本来、これだけ独立して、修正したバージョン(2.17b) とか出すべきなんですが…複数バージョンを複数の OS 向けに用意するのは、かなり面倒なもんで…今回のところはお許しを。

しかし、今回の拡張内容は基本的にどうでもよい機能ばかりだなぁ。

YACUS でバグが見つけた。「チ」の時の 2 バイト目を逆クォートとみなしてしまうのだ。そのため、チの次からコマンド名が始まっていると解釈してしまう。

日本語を扱う際、漢字を意識したコードを書くのを忘れるとすぐこんなことになるし、毎回書くことも面倒だ。やはり、char 型ベースで日本語を扱うのはよろしくない。

NYACUS では、DOS ベースでも容量を食わないはずの専用文字列クラスNnString を用意した。これによって、バッファオーバフローはソースから駆逐できたが、内部データ構造は依然 char 配列であり、上記のようなバグを駆逐できなかった。

ここはやはり１文字＝１要素となる形で、文字列クラスを作り直す必要があるだろう(歯車の再発明だ！)。

画面編集部分は従来どおりとする
NnString を使っていないし、桁数=バイト数に依存しているので、対応は難しい。ここは下手に触るとエライことになる、非常にデリケートな部分なのだ。葉山がエディタ部分の要望に難色を示す傾向にあるのは、このせいなのだ。
画面出力は多分問題なし
stdio 系ではなく、また独自のクラス(Writer)を用意している。ここで統括してなんとかできるだろう。

ただ、問題は、従来の C 言語関数を多用しているところだなぁ。char ベースの文字列クラスだと、ただのキャストでいいけど、そうでないと変換に実際に処理が入るからなぁ。
